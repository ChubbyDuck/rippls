# Linear as a ticket source

We added Linear as a second Source behind the existing `TicketSource` port, so the engine processes Linear issues with no domain change: the source converts a Linear issue into a `Ticket` on read, and converts Ticket changes into Linear writes on write. Linear has no custom-field API and no atomic claim, so the mapping uses the fields Linear does model, plus grouped labels for the rest, and a race-tolerant claim. The connection uses `@linear/sdk` with raw GraphQL and Effect `Schema` decoders, authenticated by a personal API key in the `Authorization` header verbatim (no `Bearer`).

## Mapping

- Identity: the issue UUID (stable). The `identifier` (`ENG-123`) is display-only.
- Native fields: `title`, `description` → body, Linear project → Project (slugified to a branch-safe string), issue relations → `blockedBy` (blockers from `inverseRelations(type: blocks)`).
- No native slot: `kind` and `hitl` are grouped labels, and both are hints. An issue without a `kind` label has the default Ticket Kind from config; an invalid value, or more than one `kind` or `hitl` label, makes it unreadable: the source does not offer it as a ticket, and reports it with the reason, so the Engine prints it at start and `rippls status` lists it. The source reports an unreadable issue in an `unstarted` state, and one in a `started` state that is assigned to the API-key user, which Rippls claimed; an unreadable `started` issue of anyone else, or of no one, is a person's work in progress and is not reported. Its HITL is the `hitl` label, else the HITL its stated `kind` implies, else yes. Linear has no readiness marker.
- A Ticket stores no status. The source sees an issue in a `completed` state as done; its workflow state means nothing else to the Ticket.

## Reads and writes

- The pull is team-scoped (config `teamId`). The `--project` flag narrows it to one Linear project by slug. The source offers only `unstarted` issues for processing, so a human moves an issue to Todo to make it ready — the readiness gate needs no extra label. The read of the tickets in scope also returns an issue in a `started` state, read as claimed on Linear: it is not Eligible unless this host's Ledger holds a Stale Claim on it, and then the Engine replaces that Claim (reports released, then claimed). The Claim is a saga (ADR-0004), and this replacement is its recovery. A Stale Claim on a ticket that the Ledger shows as escalated or done is not replaced to be taken: the Engine reports the end state, as above, and removes the record. When a person has taken the issue since the Engine stopped, released leaves it as it is, the claimed report fails on an issue that is not `unstarted`, and the person keeps the issue. An issue in a backlog, triage, or canceled state is never offered. A read by identity finds an issue in any state: the Engine can complete the issue it claimed, a blocker in a `completed` state is done, and a blocker in any other state is open.
- The Claim lives in the local Ledger (ADR-0004), not on Linear. The Engine reports it to the source: claimed sets assignee = viewer and the first `started` state, then re-reads to confirm. A lost race or a failed read fails the report. Its writes may have landed, so the Engine keeps the Claim in the Ledger, takes another ticket, and reports released when it exits. On exit, the Engine reports the end state that the Ledger shows (released, escalated, or done) and removes the record of a Claim only once that report succeeds, so a failed report leaves a Stale Claim that a later run finishes. Released writes only to an issue that Rippls still holds: one in a `started` state that is assigned to the API-key user. It moves the issue to the first `unstarted` state and then unassigns it. The state is written first, so a release that stops after its first write leaves an issue that is offered again, not a started one with no assignee, which no later release would change. An issue that a person has taken, or one in another state, holds no Claim of Rippls, so released leaves its assignee and state as they are.
- Complete → `completed` state, only after the merge of the Ticket Worktree succeeds, so a failed merge leaves the issue as it was. The Engine keeps the Claim in the Ledger until the issue is completed. When that write fails, the Claim stays until the Engine exits, and the exit reports done again; a later Engine that meets the record as a Stale Claim does the same. A done report writes only to an issue that Rippls still holds (started, assigned to the API-key user), so an issue already completed, or one that a person has taken, is left as it is. Unblock needs no write, because Linear derives blockers from live relations.
- The Escalation lives in the local Ledger (ADR-0004). The Engine reports escalated to the source, and removes the Claim only once that report succeeds; when it fails, the Claim stays and the exit reports escalated again, so no issue stays started with no record in the Ledger. The report unassigns the issue, moves it to the first `unstarted` state, and adds the `needs-human` label. It no longer changes the `kind` or `hitl` labels, so the issue still describes the work. The source reads an issue with `needs-human` as HITL yes, so it is not Eligible while the label stays. When the team has no `needs-human` label, the source logs a warning and the report still succeeds, because the Ledger holds the Escalation.

## Consequences

- This deviates from the lalph reference on three points: we key by UUID (not `identifier`), we pin a team (not a project), and we do not filter by assignee on the ready query.
- Metadata (viewer, per-team states, labels, projects) is cached. Each poll runs one filtered query ordered by `createdAt`, and honors the `X-RateLimit-*` headers.
- Phase one is a dedicated switch — a tagged `source` value in config and on the CLI selects the folder source or the Linear source for a run. A combined source that reads both and routes writes by the id namespace is deferred.
